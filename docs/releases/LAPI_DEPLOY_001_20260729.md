## 工具

### 部署

```powershell
ops\Deploy-LapiQueryHardening.ps1
```

执行顺序：

1. 要求管理员权限；
2. 校验 `origin`；
3. 拒绝已跟踪文件脏工作区；
4. 拉取发布分支；
5. 校验调用方提供的精确目标提交；
6. 校验生产祖先和当前本地提交祖先关系；
7. 自动识别 Windows 服务；
8. 创建受限 ACL 备份目录；
9. 备份本机环境文件、build-info、蓝奏配置、状态和查询快照；
10. 停止服务；
11. 使用 detached HEAD 切换目标提交，不移动原生产分支；
12. 安装依赖并运行完整单元测试；
13. 生成干净的 `build-info.json`；
14. 启动服务；
15. 执行新旧接口、协议、观测和快照验收；
16. 写入部署记录和验收报告；
17. 任一关键步骤失败时自动回滚。

### 验收

```powershell
ops\Test-LapiQueryHardening.ps1
```

验收范围：

- `/livez`、`/readyz`；
- `/build-info` 精确提交与 `dirty=false`；
- 旧 `/shard_query`；
- 旧 `/aram_augments`；
- 新 `/api/v1/groupguard/query`；
- 新 `/api/v1/operations/query-observability`；
- 合集、英雄目录和 ARAM 成品快照；
- 可选查封号最终下发验证。

### 回滚

```powershell
ops\Rollback-LapiQueryHardening.ps1
```

回滚不依赖远端分支移动，直接恢复部署记录中的 `previous_commit`，恢复本机文件，重新安装旧版本依赖并验证：

- 服务重新运行；
- `/livez` 和 `/readyz` 为 HTTP 200；
- `/build-info` 精确等于旧提交。

服务端必须先发布。部署验收会明确调用旧接口，证明当前 GroupGuard 在尚未迁移时不会因为服务端升级立即中断。

